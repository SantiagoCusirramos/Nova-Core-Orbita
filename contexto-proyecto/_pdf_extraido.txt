Resumen. La experiencia es una sola emergencia energética organizada en dos misiones conse-
cutivas. En la primera, el astronauta encuentra un repuesto, lo introduce en una compuerta y
utiliza una consola para sustituir el módulo mediante un sistema robótico. En la segunda, realiza
una salida EVA, usa una unidad de maniobra personal inspirada en el MMU, repara el panel solar
y regresa. El Core escalable controla 6 y 10 objetivos respectivamente; los minijuegos validan sus
pasos internamente y se comunican con Core solo al terminar correctamente.
Propósito y criterio de avance
Documento común para los cinco integrantes: narrativa, requisitos, estructura modular, contratos de
integración, roles, diagramas, pruebas y plan. “Escrito” no equivale a “integrado/probado”: los
scripts se deben compilar, configurar y verificar en Unity sobre el repositorio nuevo.

2. Concepto, narrativa y alcance
2.1 Visión del videojuego
Género: simulación espacial en primera persona. Modalidad: un jugador en VR. Meta: una
experiencia corta y completa, de duración pendiente de validación con usuarios. La historia se
estructura como una contingencia energética única, con dos reparaciones sucesivas. La victoria solo se
declara tras finalizar la segunda misión.
2.2 Introducción: despertar y alarma
1. El astronauta despierta en una zona de descanso; se utiliza un fundido visual suave sin desplazar
artificialmente la cámara del visor.
2. Se escuchan alarmas y aparecen señales de emergencia.
3. El Centro de Control informa que existe una anomalía en la distribución eléctrica.
4. El jugador recibe controles básicos y se dirige al centro de mando.
5. El sistema narrativo inicia Core mediante StartMission() una sola vez, en el momento definido
por el equipo.
Implementación prevista: GameIntroManager.cs, independiente de Core, con Diogo (escena-
rio/luces), Camila (voz/UI), Santi (comodidad VR) y Luis (arranque). Estado: no confirmado como
implementado.

2.4 Base de realismo y adaptación educativa
La sustitución robótica toma como referencia general operaciones de retirada y reemplazo de unidades
mediante equipos robóticos de la ISS; el componente y la operación concreta dentro del juego son
una adaptación ficticia. El MMU existió históricamente como unidad de maniobra, pero no es un
vehículo de traslado rutinario en las EVA actuales. El minijuego del panel rasgado con refuerzos es
una propuesta inicial, inspirada en reparaciones históricas; el equipo aún debe decidir su mecánica
final. Ninguna secuencia del juego debe presentarse como procedimiento NASA real ni entrenamiento
operativo.

5. Core: arquitectura y contrato público
5.1 Componentes existentes a nivel de código
Archivo Función
MissionState.cs Define los estados NotStarted, InProgress y Completed.
MissionAction.cs Define acciones reconocidas; se agregaron las acciones de compuerta,
consola, MMU, llegada y verificación final.
MissionObjective.cs Clase [Serializable] con objectiveId, description y
requiredAction.
MissionDefinition.cs ScriptableObject con ID, nombre, descripción y lista ordenada de
objetivos.
MissionManager.cs Gestor singleton que recibe acciones, avanza objetivos, cambia de
misión y emite eventos.
MissionActionBridge.cs Adaptador entre interacción y gestor; expone ExecuteAction() y
TryExecuteAction().
MissionDebugTester.cs Utilidad de pruebas manuales de acciones, inicio, reinicio y progreso.
5.2 Regla de transición y datos
MissionManager tiene una lista ordenada de MissionDefinition y dos índices: misión y objetivo
actuales.
TryCompleteAction(action) devuelve true solo si la secuencia está en progreso y la acción coincide
con CurrentMissionObjective.RequiredAction.

8. Protocolo de integración para cada compañero
8.1 Contrato mínimo obligatorio
1. El sistema externo verifica su interacción y condiciones físicas o lógicas.
2. Desde un UnityEvent se llama a ExecuteAction() del puente. Desde C# se puede utilizar
TryExecuteAction() para obtener true o false.
3. El puente busca MissionManager y entrega MissionAction configurada.
4. Core devuelve true/false; si acepta, cambia objetivo o misión y comunica eventos a la UI.
5. Ante OnMissionReset, el sistema externo restituye objetos, controles y estados locales. No debe
emitir automáticamente acciones durante el reinicio.

8.3 Reinicio, errores y contratos adicionales
Acción fuera de orden: Core devuelve false. El objeto no debe cambiar a “completado” si la
acción fue rechazada.
Una sola emisión: el minijuego evita disparar repetidamente el evento de éxito (y debe manejar
correctamente los reintentos tras reiniciar).
Origen confiable: validar objeto, zona, pose y estado local antes del envío; Core hoy solo coteja el
enum.
Eventos de UI: Camila se suscribe/desuscribe correctamente; no modificar índices ni el enum
desde UI.
Consola VR: deshabilitar solo traslación/teleportación cuando corresponda, mantener libre el
tracking de cabeza, y restaurar locomoción al salir o al reiniciar.
Cambio de misión: la misión 1 finaliza con RepairConfirmed; Core emite OnMissionChanged
para iniciar misión 2 y no emite aún OnMissionCompleted.
